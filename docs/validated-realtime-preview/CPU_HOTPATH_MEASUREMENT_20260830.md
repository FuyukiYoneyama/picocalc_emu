## 0. 目的と結論の要約

過去資料には、`exact`モードのCPU単体経路を **33.63 host cycles / emulated cycle**（≒111.7 MHz）
とする記載があった。しかし、その値の測定コマンド、ホスト、日時、source SHA、raw logは現在確認
できない。本書はその値を再現した測定記録ではなく、旧`basic`差分分析の履歴である。

旧値の出典と現行の直接測定値は、[`RP2040_CPU_MEASUREMENT_LEDGER_20260903.md`](../RP2040_CPU_MEASUREMENT_LEDGER_20260903.md)
に整理している。

本計測で分かったこと。

1. **`step()`の内側が全体の約2/3、外側のドライバループが約1/3。**
2. **例外ポーリングが単独で15〜17%** — ほとんど何もしていないのに、単一項目として最大。
3. **既存のOPT4プロトタイプ3種のうち2種は、この負荷では効果が測定誤差以下。**
4. **全体の約半分が、どの機構にも帰属できていない。**

4が最大の未解決事項であり、サンプリングプロファイラなしには前へ進めない。

## 1. 計測環境と手法

### 1.1 サンプリングプロファイラが使えなかった経緯

`samply`のインストールは成功した（`cargo install samply`、`~/.cargo/bin/samply`に存在）。しかし
WSL2の`kernel.perf_event_paranoid = 2`が非特権プロセスの`perf_event_open`を拒否するため、
実行できなかった。解除には`sudo`が必要で、これはシステムのセキュリティ設定変更にあたるため、
自動実行せず所有者の判断へ委ねた。

`perf`本体はインストールできない。WSL2は独自カーネル
（`6.18.33.2-microsoft-standard-WSL2`）を使っており、対応する`linux-tools`パッケージが存在しない。

### 1.2 採用した手法: 差分測定

1. `rsync`でリポジトリを`/tmp/pb-scratch/repo`へ複製（`target/`除外）
2. 疑わしい処理を`#[cfg(feature = "...")]`で潰すscratch専用featureを追加
3. **production profile**（`opt-level=3, lto="fat", panic="abort"`）でビルド
4. `paced_bench_rp2040 --workload basic --unpaced --model serial`のMHz中央値を比較
5. マシンノイズのドリフトを打ち消すため、変種を交互に実行

**本番リポジトリ（`picoem-picocalc`）は一切変更していない。** commit、push、CI実行、
システム設定変更のいずれも行っていない。

`profile.profiling`（`lto = false`）ではなく実運用のreleaseプロファイルで計測しているため、
数値は実際に動くバイナリに対応する。

### 1.3 計測環境

| 項目 | 値 |
|---|---|
| ホストCPU | AMD Ryzen 5 5600X（6コア / 12スレッド） |
| 基本クロック | 3.70 GHz（TSC較正値 3692 MHz と一致） |
| 実行時クロック | 約4.32 GHz（ブースト） |
| カーネル | `6.18.33.2-microsoft-standard-WSL2` |
| run間ジッタ | **アイドル時でも約5〜8%** |

**注意:** 旧資料は`33.63 host cycles`をTSC単位として扱っていたが、元のraw runがないため、
この換算（および111.7 MHz）の再現性は確認できない。

### 1.4 `basic`ワークロードの正体

```text
MOVS R0, #1        （1回だけ）
loop:
  ADDS R0, R0, #1  （1 cycle）
  B .-2            （3 cycles、パイプラインフラッシュ）
```

**実行されるPCは2つだけ**で、最初の2命令以降デコードキャッシュは常時ヒットする。
ループ内に`LDR`/`STR`が無いため、**データバスの境界チェックはこの負荷では一切実行されない。**

したがって本計測の結論は`basic`負荷に限定される。`peripheral`／`contention`／`stress`は未計測。

## 2. 測定結果

この旧`basic`差分分析のlocal baselineは **約114〜116 MHz**（≒34.4〜34.8 host cycles/emu cycle）
だった。別ホストの111.7 MHz / 33.63は、出典未確定の過去記載であり、整合性の根拠には使わない。

| 変種 | 中央値 MHz | ベースライン比 |
|---|---:|---:|
| ベースライン（無改変） | ~115 | — |
| **床: `step()`をサイクル加算のみに縮退**（例外ポーリング・キャッシュ参照・フェッチ・ディスパッチ・実行をすべて除去。外側ループは維持） | **~335** | **+190%** |
| 例外ポーリング除去（`core/mod.rs:291`） | ~133 | **+15〜17%** |
| フラグ計算除去（`core/execute.rs:119`、`add_with_carry` + `set_nzcv`） | ~129 | **+11%** |
| 上記2つ同時 | ~147 | +29% |
| OPT4-E `compact-dispatch-key-prototype` | ~119 | +4〜5% |
| OPT4-D `diagnostic-pc-compile-out-prototype` | ~115 | **±0（ノイズ範囲）** |
| OPT4-A `unconditional-cache-lookup-prototype` | ~116 | **±0（ノイズ範囲）** |
| 上記5つすべて同時 | ~137 | +21%（**劣加算的**） |

## 3. 分析

### 3.1 コストの2分割

床テスト（`step()`が何もしなくても外側ループは回る）が **~335 MHz** に達したことから:

- **`step()`の内側（例外ポーリング＋キャッシュ参照＋ディスパッチ＋命令実行）が約2/3**
- **外側`step_serial_with_external`のループ機構が約1/3**

外側には、単一コア負荷でも毎命令実行される次が含まれる（`lib.rs:957-1000`）。

- `is_halted()`／`wfe_waiting`判定（両コア分）
- `set_active_core`
- `drain_cache_invalidations`
- `finish_watchdog_trigger`
- `maybe_wake_core1`
- **core 1停止中でも`end_core1_step()`**（`lib.rs:993`）

事前の静的解析では、この外側ループの毎命令オーバーヘッドが最有力候補と目されていた。
**実測はそれを否定し、支配的なのは`step()`内側であることを示した。**
静的解析だけで投資先を決めていれば誤っていた。

### 3.2 例外ポーリングが最大の単一項目

`try_take_any_pending_exception`（`core/mod.rs:354-399`）は、`primask & 1 == 0`で短絡し、
ICSRの2ビットテストとNVICの`pending & enabled == 0`判定で即座に`None`を返す。ループは無く、
数個のロードとビット演算のみである。

**それを除去するだけで15〜17%改善する。** これは処理内容に対して不釣り合いに大きい。

計測担当の見立ては「**処理自体が遅いのではなく、インライン化されていない、あるいは呼び出し境界
のエイリアシングが周辺コードの最適化を妨げている**」。逆アセンブルによる確認は行っていないため、
**この解釈は未検証である。**

### 3.3 既存OPT4プロトタイプの効果は限定的

`unconditional-cache-lookup-prototype`と`diagnostic-pc-compile-out-prototype`は、この負荷では
**測定誤差の範囲内で効果なし**。3つ合わせて4〜5%で、その全部が`compact-dispatch-key`由来である。

これは有用な否定的結果である。OPT3-C（4.15%、5%基準未達で棄却）とほぼ同じ値が再現されており、
**過去のCPU最適化の努力は、この負荷の実際のボトルネックを狙えていなかった**ことを示す。

`compact-dispatch-key`が伸びない理由として、LLVMが`opcode >> 11`のmatchに対して既にジャンプ
テーブルを生成しており、キャッシュ済みキーとほぼ同速になっている可能性が挙げられているが、
これも未検証である。

### 3.4 効果は劣加算的

2つ同時（例外ポーリング＋フラグ）は+29%で、単独値からの素朴な予測（1.17×1.11≒+30%）とほぼ一致
する。しかし**5つすべてでは+21%**と、2つの場合を下回った（2回測定して再現）。

共有ボトルネック（命令キャッシュ圧、コード生成の相互作用など）の存在を示唆するが、特定できて
いない。

### 3.5 帰属できない約半分

床までの必要幅が約66ポイントに対し、特定できたのは25〜29ポイントである。
**残り約半分がどの機構に属するか不明である。**

候補として挙げられているもの（いずれも未検証）:

- `matches_pc`とエントリコピー（`core/decode.rs:296-314`）
- `execute_thumb16`のmatch自体
- `thumb16_branch`の`sign_extend`／`read_pc`／分岐先計算（`core/execute.rs:985-991`）
- `step → decode_execute → execute_thumb16 → handler`の呼び出し連鎖における
  `CoreBus`トレイト境界を跨ぐディスパッチとインライン化の効果

**サンプラまたは逆アセンブルなしには、これ以上絞り込めない。**

## 4. 2.24倍達成の見込み（旧試算・現行判断には使用しない）

旧資料の`exact`モード試算では、PicoCalc（250 MHz）の1倍に到達するには、115 MHz → 約258 MHz
（**2.24倍**）が必要とした。この起点は111.7 MHz周辺の旧記載に依存しており、現行のCPU基準値ではない。

**可能性はあるが、現時点で根拠は不十分である。**

| 論点 | 状況 |
|---|---|
| アーキテクチャ上の余地 | **ある**。床が~335 MHz（現状の2.9倍）なので、外側ループ構造が2.24倍を阻んではいない |
| 実測で到達した最大値 | **~150 MHz（1.3倍）** にとどまる |
| 最も効いた2項目 | 例外ポーリングとフラグ計算。**どちらも正確性に不可欠で削除不可**。「安くする」ことしかできず、削除ほどの効果は出ない |
| 最大のリスク | **帰属不明の約50%**。何か分からない以上、修正可能かすら判断できない |

2.24倍には、判明した複数項目の改善を積み上げたうえで、**さらに未特定の部分に手を入れる必要が
ある**と考えられる。

## 5. 次の作業

### 5.1 最優先: サンプリングプロファイルの取得

差分測定は**候補を事前に推測する必要がある**。今回は例外ポーリングとフラグ計算を
コードリーディングから選んで当たったが、残り50%は推測では届かない。サンプラなら
「その他」のバケツを直接特定できる。

必要な設定変更とツールは§6に記す。

### 5.2 サンプラ取得後に確認すべきこと

1. 帰属不明の約50%がどこにあるか
2. 例外ポーリングの15〜17%が本当にインライン化の問題か（逆アセンブルで確認）
3. `compact-dispatch-key`が伸びない理由（LLVMのジャンプテーブル生成の確認）
4. 劣加算性の原因（共有ボトルネックの特定）

### 5.3 採用基準について

過去のOPT2／OPT3／OPT4は「単独で5%改善」を採用基準としていた。本計測は、その基準以前に
**狙う場所が正しくなかった**可能性を示している。基準の見直しを議論する前に、まず
サンプリングプロファイルで正しい対象を確定すべきである。

## 6. 所有者にお願いしたい設定変更とツール

以下はいずれも**私からは実行しない**。システム設定の変更とパッケージ導入は所有者の判断による。

### 6.1 必須: `perf_event_paranoid`の緩和

```sh
sudo sysctl -w kernel.perf_event_paranoid=1
```

現在の値は`2`（非特権プロセスの`perf_event_open`を全面的に拒否）。`1`にすると
ユーザー空間のプロファイリングが可能になる。カーネル空間のシンボルまで見る場合は`0`が要るが、
**本件はユーザー空間のみで足りるため`1`で十分**である。

再起動で元に戻る。恒久化する場合は`/etc/sysctl.d/`へ設定を置くが、**一時的な`-w`で十分**である。

補足: `kernel.kptr_restrict`は現在`1`だが、ユーザー空間プロファイルには影響しないため
変更不要である。

### 6.2 既にインストール済み（追加作業不要）

| ツール | 場所 |
|---|---|
| `samply` | `~/.cargo/bin/samply` |
| `objdump` | `/usr/bin/objdump` |
| `addr2line` | `/usr/bin/addr2line` |

**§6.1の設定変更だけで`samply`が動く見込みである。** 追加インストールは不要かもしれない。

### 6.3 あると有用（任意）

| ツール | 用途 | 導入方法 | 必要性 |
|---|---|---|---|
| `linux-perf` | `samply`が動かない場合の代替 | `sudo apt install linux-perf` | WSL2独自カーネルのため**動作しない可能性が高い**。まず`samply`を試すべき |
| `cargo-asm` または `cargo-show-asm` | 例外ポーリングのインライン化状況を関数単位で確認 | `cargo install cargo-show-asm` | **中**。§5.2の2番を直接確認できる。sudo不要 |
| `hyperfine` | ベンチ実行のばらつきを統計的に扱う | `cargo install hyperfine` | 低。現状の交互実行でも足りている |

### 6.4 推奨する順序

1. `sudo sysctl -w kernel.perf_event_paranoid=1` を実行
2. `samply record ./paced_bench_rp2040 --workload basic --unpaced --model serial` が動くか確認
3. 動けば、それだけで§5.2の1〜4に着手できる
4. 動かない場合に限り、§6.3の代替を検討

## 7. 本計測が主張しないこと

- `basic`以外のワークロード（`peripheral`／`contention`／`stress`）については何も測っていない
- UXモードの速度については何も測っていない。本計測は`exact`モードのCPU経路のみが対象である
- 帰属できた25〜29ポイントについても、**実際に安全に改善できるとは示していない**。
  例外ポーリングもフラグ計算も正確性に不可欠であり、除去は不可能である
- 1倍達成の可否について、結論は出していない
