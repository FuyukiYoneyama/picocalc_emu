## 0. この文書の位置づけ

Validated Realtime Previewで1倍のUX検証を実現するための考え方を記録する。

**これは概念であり、正典計画ではない。** 現在の正典計画
（[`../VALIDATED_REALTIME_PREVIEW_IMPLEMENTATION_PLAN_20260828.md`](../VALIDATED_REALTIME_PREVIEW_IMPLEMENTATION_PLAN_20260828.md)）
は`exact`モードのみを前提としており、本書の方針は未採用である。採用する場合に必要な
計画側の修正点は§10に示す。

数値は各資料のスコープに従う参考値であり、旧111.7 MHz／44.7%は出典未確定の過去記載である。
`ux`モードそのものの測定は未実施である。
本書を根拠に`realtime-1x-qualified`やpreviewのcapability昇格を主張してはならない。

## 1. 中核となる考え方

**検証用バージョンとUX用バージョンを分けて構築する。**

| | 検証用（`exact`、既存） | UX用（`ux`、新規） |
|---|---|---|
| 目的 | 適合性の判定 | 人間による体感評価 |
| 正確性の担保 | 自身がサイクル厳密 | **対象UF2が事前にPASS済みであること** |
| 速度 | 問わない（現状14.6%） | **1倍に近いこと** |
| 出力 | report、digest、verdict | 画面・音・操作応答のみ |

正確性の保証が**時間軸で分離**されている。先に`exact`が「実機で動く」ことを確定し、
その事実を前提として`ux`が高速に走る。**`ux`自身が正確である必要はない。**

### 1.1 これは偽装ではない

性質の異なる2つを区別する。

- **正確さを装って端折る** — 「1倍で動いた」と主張しながら裏でイベントを捨てる。これは偽装。
- **目的の異なる別モードとして端折る** — 保証の出所が事前検証にあり、自身は証拠を生成しない。

後者を成立させる構造的な条件は一つである。

> **`ux`モードは検証証拠を一切出力しない。**
> report、digest、verdictを生成せず、target registryの合否判定に関与しない。

証拠を生成しないモードは、偽の証拠を作れない。禁止規定ではなく**出力の不在**で担保する。

## 2. 何を端折り、何を守るか

### 2.1 端折ってよいもの

- サイクル厳密な時間会計。命令は実行し、時間は近似で進める
- PIOによるLCD転送のビット単位再現
- PSRAMの`step_quantum=1`強制
- SRAM bank contention判定
- behavior digest／observation projectionの生成

### 2.2 端折ってはいけないもの

- 画面に表示される内容（UX評価の対象そのもの）
- キー入力への応答
- 音声の内容と体感的タイミング
- ハング・クラッシュの再現

## 3. LCD転送 — 過程ではなく結果を作る

### 3.1 現状の構造

```text
DMA → PIO TX FIFO → PIOがSCK/MOSIをビットトグル → wireがバイト復元
    → St7365p::transfer_byte() を1バイトずつ → framebuffer
```

320×320×2バイトで、**1フレームあたり204,800回の`transfer_byte()`**が発生し、
その手前にビット単位のPIO実行がある。

### 3.2 UXモードの構造

```text
DMAの転送設定を検出（転送元アドレス・長さ・宛先＝PIO TX FIFO）
    → 転送元メモリを直接読む
    → St7365pの現在のウィンドウとカーソルへ一括書き込み
    → カーソルを転送分だけ進める
    → 仮想時間を転送相当分だけ進める
```

**画面に出る結果は同一で、ビット遷移とバイト単位ループだけが消える。**

### 3.3 これが成立する理由

`St7365p`は既に必要な状態をすべて保持している。

- ウィンドウ: `col_start` / `col_end` / `row_start` / `row_end`
- 書き込みカーソル: `x` / `y`
- カーソル前進とラップアラウンドのロジック

一括書き込み後にカーソルを進めるだけで状態は整合し、その後にコマンドやRAMRDが来ても
矛盾しない。

### 3.4 経路ごとの扱い分け

| 経路 | 量 | UXモードでの扱い | 理由 |
|---|---|---|---|
| ピクセル書き込み | 1フレーム204,800バイト | **一括転送へ置換** | 唯一の巨大コスト |
| コマンド（CASET/RASET等） | 数バイト | 従来通り1バイトずつ | 量が小さく、ウィンドウ状態の維持に必要 |
| RAMRD読み戻し | 稀・少量 | **従来通り** | CPUがブロックしており体感に影響しない |

**速くする必要があるのは1つだけ**である。`transfer_byte()`は残り、既存の繊細なRAMRD
semanticsには触れない。追加するのは並行する高速パスであって、既存コードの書き換えではない。

## 4. ハードウェアと一体でブロック化する

### 4.1 LCD転送とCPU待機は同一のイベントである

`bsp/src/display_pio_rgb565.cpp`の構造がこれを示す。

```text
lcd_rgb565_pio_write_blocking(...)   ← blocking
lcd_rgb565_pio_wait_dma()            ← DMA完了を待つ
```

**現在のエミュレーターは1回の転送に対して2つのコストを別々に払っている。**

1. デバイス側: PIOのビットトグルと`transfer_byte()`の反復
2. CPU側: `write_blocking`のポーリングループ

§3のLCD一括化は**1だけ**を消す。**2は残り**、CPUはポーリングループを回り続ける。

**両方を1つの単位として畳めば、転送も待機も同時に消える。**
片方ずつ実装すると、2回目の作業で1回目の構造を作り直すことになる。

### 4.2 畳み方

```text
lcd_rgb565_pio_write_blocking への進入を検出
    → 転送元・長さ・LCDウィンドウから結果を確定
    → framebufferへ一括書き込み（デバイス側を畳む）
    → CPUのPCを関数の出口へ進める（CPU側を畳む）
    → 仮想時間を転送相当分だけ進める
```

CPUのポーリングループを実行せず、関数の出口へ直接飛ばす。アプリから見れば
「関数が返ってきた」だけで辻褄は合う。

### 4.3 既に同じ原理が実装されている

OPT1-A `exact idle fast-forward`は、**全体がアイドルのときに一気に時間を進める**機構であり、
promoted済みである。全サイクルの67%がこれで畳まれている。

本節の提案は、その原理を**「全部アイドル」から「ハードウェア完了待ち」へ拡張する**ものである。
新機軸ではなく、実績のある手法の適用範囲拡大として位置づけられる。

### 4.4 安全に実装できる条件

パターン認識で関数を畳む手法は、対象バイナリが想定と違うと壊れる。本プロジェクトには
防御が揃っている。

- **BINがBSP版とgitコミットを保持する**（`[PICOCALC][BOOT] bsp=... bsp_git=...`）
- **Canonical BSPは版が固定**され、生成プロジェクトはBSPを改変しない規約である
- したがってBSPの`write_blocking`／`wait_dma`が**どんなコードになるかが既知**である

**一致しなければ従来経路へフォールバックする。** 速くならないだけで、動作は変わらない。
同じ原則をDMA非経由の直接FIFO書き込みなど、想定外の経路にも適用する。

## 5. CPU側 — ブロック単位の実行

### 5.1 考え方

`.bin`をコードブロック単位で中間表現へ解釈し直して実行する（動的バイナリ変換／
basic-block JIT）。UXモードではサイクル厳密性が不要なため、次が許される。

- サイクル会計をブロック単位にまとめる
- 割り込みチェックをブロック境界で行う
- ブロック同士を直結する（ブロックチェイニング）

`exact`モードでは絶対にできない省略であり、UXモードだからこそ成立する。

### 5.2 既存の実測が示す制約

OPT3-Aの計測（PicoTetris、immutable XIP）:

| 連続実行長 | 命令の割合 |
|---:|---:|
| ≥2命令 | 99.98% |
| ≥4命令 | 50.34% |
| ≥8命令 | 27.29% |
| ≥16命令 | 13.52% |
| ≥32命令 | **0.55%** |

**平均4.563命令**でブロックが切れ、終了の大半は分岐である。ブロック変換は入口・出口の
オーバーヘッドをブロック内命令数で償却する技術なので、**この長さでは償却が効きにくい**。

またデコードキャッシュは既にヒット率99.83%で機能しており、OPT3-Cの事前デコード改善は
4.15%にとどまり5%基準未達で棄却されている。**この方向の細かい改善の伸びしろは小さいことが
実証済み**である。

### 5.3 §4との関係

§4のブロック化を先に行うと、この制約の意味が変わる。ポーリングループは
「4.5命令のブロックを何百万回」という形で現れるため、**§4がそれを畳めば、
5.2の分布そのものが変化する**。

したがってCPU側のブロック単位実行は、**§4の後に、残った実計算に対して**評価するのが
順序として正しい。

## 6. 到達点の見通し

OPT2-Dの実測内訳（PicoTetris）:

| 区分 | 全サイクル比 | 現在の扱い |
|---|---:|---|
| アイドル | **67%** | OPT1-Aで既に畳まれている |
| running かつ PIO稼働 | **約23%** | §3・§4の対象 |
| running かつ PIO非稼働 | 約10% | §5の対象 |

旧資料では、`exact`モードの理論上の天井を周辺機器コスト0で**44.7%**
（111.7 MHz ÷ 250 MHz）と記載していた。しかし111.7 MHzのraw provenanceがないため、これは
検証済みの天井ではなく、現在の計画や採否の基準に使わない。

この旧44.7%は「250Mサイクルを全部実行する」前提の試算である。§4で23%区間を畳み、
67%が既に畳まれているなら、**実際に実行すべきサイクル自体が大幅に減る**。
その場合、必要なスループットも比例して下がる。

**1倍は射程内と考えられる。ただしこれは推論であり、UXモードの実測は未実施である。**

## 7. 検討順序

```text
段階1: hwspi-rgb888 で測る                    実装ゼロ
段階2: LCD転送＋CPU待機を一体でブロック化      最大の効果が見込まれる
段階3: 残る実計算にブロック単位実行            profile後に判断
```

### 段階1が先である理由

`bsp/CMakeLists.txt`より:

| バリアント | ゲストクロック | CPU天井 | LCD方式 |
|---|---:|---:|---|
| `hwspi-rgb888` | 125 MHz | 旧試算（出典未確定） | ハードウェアSPI（PIO不使用） |
| `pio-rgb565`（推奨） | 250 MHz | 旧試算44.7%（出典未確定） | PIO |

**コード変更なしで、PIOを使わない場合の到達点が測れる。** 段階2の効果見積りの材料
になる。ただし表示形式が変わるため、UX評価の対象として妥当かは別途判断が必要である。

### 段階3の前提

CPU単体経路（`--workload basic`）の旧記載にある33.63ホストサイクル／エミュサイクルは、
raw provenanceがないため現行の基準値として扱えない。旧分析ではディスパッチ、サイクル会計、
contention判定、バスアクセスの配分が分からないまま実装へ進むべきではない。

## 8. 既存資産への影響

**`exact`モードには一切触れない。** UXモードは証拠を生成しないため、既存の検証契約、
target registry、digest gate、machine API schema 1はすべて無傷である。

VRP-0〜VRP-4で構築したreceipt、admission、descriptor consumer、GUI、PicoCalc skin、
UART0 console、bounded audio monitorは、いずれのモードでも必要な共通基盤であり、
そのまま活きる。

## 9. 採用する場合に必要な計画修正

現在の正典計画は`exact`モードのみを前提としており、本書の方針とは次の箇所で矛盾する。
採用するなら計画側を先に修正する。

| 計画の箇所 | 現在の記述 | 必要な修正 |
|---|---|---|
| §1 判定1 | validationで使ったbyte-identicalな`picocalc-run`を起動する | byte-identical要求を`exact`モードに限定し、`ux`モードは別ビルドを許可する |
| §3.1 | GUIがemulatorを直接linkするとbyte-identicalにできない | 同上。`ux`モードは別実装として扱う |
| §5 VRP-7 | CPU cycle、IRQ、PIO、DMA、device eventを飛ばして1倍を偽装しない | 「`ux`モードは検証証拠を生成しない。`exact`モードでは一切端折らない」へ書き換える |
| §8 中止条件 | 1倍未達を隠すsemantic shortcutが必要になった | 削除する。`ux`モードの設計そのものに該当するため |
| §9 完成の定義 | `realtime-1x-qualified`の対象が`exact`経路 | `ux`モードの指標として定義し直す。`exact`の速度とは別の数字である |
| VRP-5 | 1倍qualificationの対象 | `ux`モードへ変更する |
| LOAD-0 | `exact`モードでの1倍判定に使用 | `ux`モードの負荷試験として位置づけ直す |

差分の一覧と背景は
[`../VRP_DUAL_BUILD_CORRECTION_ADVICE_20260830.md`](../VRP_DUAL_BUILD_CORRECTION_ADVICE_20260830.md)
にある。

## 10. 未確定事項

本書は概念であり、次はいずれも未確定である。

- 転送検出をDMAレベルで行うかPIO TX FIFOレベルで行うか
- 仮想時間の進め方の具体的な算出規則
- BSP関数の認識方法（アドレス、シグネチャ、その他）とフォールバック条件
- `ux`モードと`exact`モードで画面・音・入力応答が体感上一致することの確認手順
- 段階1〜3それぞれの工数
- UXモードでの`realtime_percent`の実測値

これらは設計段階で確定する。本書は方向性のみを記録する。
