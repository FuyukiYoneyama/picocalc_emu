# ドッグフーディング記録: PicoTetris（2026-08-05）

## 目的

このプロジェクトの第一目的は「AIがPicoCalc向けプログラムを自ら観測・検証・修正
できること」である。Milestone 1完了時点で標準templateのスモークは通るようになった
が、**実際にアプリを書いて作り切れるか**は一度も試していなかった。

そこでテトリス風ゲームを1本、**実機を一度も使わずエミュレーターだけで**作った。
目的はゲームそのものではなく、**ワークフローのどこに穴があるかを見つけること**である。

## 結果: 作れた

`app/main.cpp`のみ（約420行）で完成した。BSPは一切変更していない。公開APIの
`display`・`keyboard`・`audio`だけを使っている。

エミュレーター上で確認できたもの:

- 10×20の井戸、7種類のピース、4方向の回転形状
- 落下、左右移動、回転（壁蹴り付き）、ソフトドロップ、ハードドロップ
- 着地判定、ライン検出、スコア表示（自作5×7フォント）
- ゲームオーバー判定と表示
- キー入力が実際にゲームを操作する

**実機は一度も使っていない。** ビルド → エミュレーター実行 → PNG確認、の反復だけで
書けた。これは`picocalc_emu`が目指した状態そのものである。

## 見つかった穴

### 1. キー入力のタイミングを制御できない（最も重い）

`--keys "aaa "`は文字列を起動時に一括でFIFOへ積むだけで、**ゲームの状態を見て
次の操作を決められない**。結果として次ができない。

- 「ピースが着地したら次のキーを送る」
- 「この形が出たら左に3つ、それ以外は右に2つ」
- **ライン消去を意図的に起こす**

実際、ライン消去のロジックは書いたが**エミュレーター上で発火させられなかった**。
ハードドロップを連打すると全ピースが同じ列に積まれ、横移動を混ぜても列の割り当ては
運任せになる。コードの正しさは目視レビューに頼っている。

→ **Milestone 3のscenario runnerが必要**。キー投入を「いつ」「何を条件に」行うかを
記述できないと、条件付きの動作は検証できない。

### 2. 画面の検証が目視のみ

私がPNGを見て「グリッドが見える」「ピースが左に寄った」と判断している。
機械的な合否がない。次のような表明ができない。

- 「(3,19)のセルがマゼンタである」
- 「スコア領域が0以外を表示している」
- 「前フレームとの差分が井戸の内側だけである」

→ pixel/region assertionが要る。これもMilestone 3の範囲。

### 3. アプリのロジックをホストで単体テストできない

ライン消去や衝突判定は純粋な関数だが、テストするにはRP2040バイナリを作って
エミュレーターで走らせるしかない。ホスト側でリンクして直接呼べれば、
`clear_lines()`に盤面を渡して結果を検査できる。

→ Milestone 2のhost backendの価値はここにある。当初「firmware backendがあるので
優先度が下がった」と評価したが、**アプリのロジック検証という別の用途がある**。

### 4. 途中経過が見えない

取得できるのは最終フレームのPNGだけである。「30秒時点でどうなっていたか」を
見るには、サイクル数を変えて実行し直すしかない。アニメーションや状態遷移を
追う用途には向かない。

→ 定期スナップショット、あるいは指定サイクルでのフレーム取得。

## 副次的な発見

- `--lcd-variant`の既定はB。A系統のファームウェアで既定のまま走らせると
  per-cycle GPIO観測が有効になり到達サイクルが約1/3になる（本文書とは別に
  `IMPLEMENTATION_STATUS.md`へ記録済み）。
- `constexpr`配列の範囲for文に`<initializer_list>`が要る。テンプレートは
  これをincludeしていないため、最初のビルドがエラーになった。テンプレート側で
  includeするか、READMEに書くかは判断が要る。

## 次に作るべきもの（この記録からの結論）

優先順位は上の穴の重さに従う。

1. **scenario runner**（Milestone 3） — 条件付きのキー投入と、pixel/region
   assertion。これがないと「特定の状況を作って検証する」ができない。
2. **host backend**（Milestone 2） — アプリのロジックをホストで単体テストする。
   当初の想定（高速反復）より、こちらの用途の方が実利がある。
3. 定期スナップショット — 途中経過の観測。
