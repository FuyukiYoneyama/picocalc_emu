## エミュレーター本体の修正

両実行経路が共通のRP2040除算器を使い、全operand書き込みでの再開始、
商だけでのDIRTYクリア、8cycle完了時のREADY遷移、結果書き込みによる中断を

レジスター・CPU・固定SDKの除算assemblyで回帰確認済みです。
[本体修正と受入記録](https://github.com/FuyukiYoneyama/picoem-picocalc/blob/d91f2bb7189b3a534cec01f8ae3670fd3a22297a/docs/rp2040_sio_divider_fix_20261012.md)

## 修正前の不具合と影響（履歴）

修正前のbackendのSIO除算器は、除数の書き込みでは計算しますが、被除数の書き込みでは
再計算しません。RP2040はどちらのオペランドを書いても計算を開始する仕様です。
符号なし・符号付きの被除数レジスターが両方とも該当します。

追検証でmain `121d649`のSerial `Sio`とThreaded `WorkerBus`を直接呼び出し、
両方で不具合を再現しました。例えば、0÷3で初期化した後に被除数を10へ更新すると、
期待値は商3・余り1ですが、実測は商0・余り0です。
CPU命令・ClockCalc・worker threadは実行していません。

公開backend `32d27ff4179a993ae9fac6ff4a1d5e8999570fa9` と、今回の環境センサー
付き観測に使った `f810d059958773d1b42a1c6d03cc15183cdc1a4f` のソースに同じ
欠落を確認しました。全履歴・RP2350・Threadedの並行実行まで確認したという意味ではありません。

Pico SDKの64bit除算には、除数→被除数の順で書き込む処理があります。この順序で
古い結果を使うため、商の補正ループが長時間進み、画面更新や入力処理が止まった
ように見える可能性があります。backendの実装箇所、SDKの固定版参照、最小再現手順、
修正後の受入条件は
[backendの不具合文書](https://github.com/FuyukiYoneyama/picoem-picocalc/blob/main/docs/rp2040_sio_divider_bug_20261012.md)
を正典とします。

## 初回のアプリ観測（履歴）

ClockCalc 0.8.78をcleanなf810d059、Serial、quantum 1で実行し、電卓からEscで
時計へ遷移させました。2,680 ms時点で時計の時刻領域は非黒画素0、scenarioはfail。
reportの最終PCは `0x10016e40` です。初回調査ではSDK除算の補正ループ内と
対応付けましたが、その対応付けを追認する証拠には下記の制約があります。
例外・emulator error・unsupported MMIOは報告されていません。

UARTはBMP280のADC値、校正値、温度補正結果まで出ています。別の0.8.77診断runは
最終PC `0x10016cca` を記録しています。初回調査ではこのPCを同じ除算処理に、
保存LR `0x1000cab9` を圧力補正の呼び出し元に対応付けました。

**対応付けの証拠の制約:** 保存report・register dumpからアドレスは確認できますが、
対応するELF、そのSHA-256、map／symbol表、アドレス照合・逆アセンブルの出力は
保存資料にありません。関数名との対応は初回調査の記録であり、保存資料だけでは
追認できません。今回のレジスター診断も、この対応を再確認したものではありません。
元のELFを回収した場合はそのSHAと照合コマンド・出力を保存します。新しいbuildの
アドレスを、過去のBINのアドレス照合に代用することはできません。

【推定】 上記モデルの欠落が今回の除算停滞を説明します。ただし修正版による比較runは
未実施です。ユーザーが報告した実機LCDの故障原因とは断定しません。

0.8.73のbaselineは非黒画素数のassertでpassでしたが、時計snapshotに電卓の残像が
あります。単なる非黒画素数では期待した画面の表示を保証できません。
また、LCDのCOLMODやSLPOUTが正しく記録されても、実機の表示成功を保証しません。

## 修正前のレジスター追検証（2026-10-12）

backendの無変更main `121d649930d625924fa7608a3b72ed622098f522`に依存する
独立した診断プログラムを `/tmp` でビルドしました。Threaded経路はWorkerBusを
ホストの同じスレッドから順に呼び出しており、並行動作の検証ではありません。

各経路17項目を確認し、Serialは11項目、WorkerBusは10項目で仕様と不一致でした。
これは確認項目数であり、別々の不具合が21件あるという意味ではありません。
実行終了0は観測の保存完了を示し、適合判定は各行の `matches_spec` で示します。

| 確認 | Serial／WorkerBusの実測 | 判定 |
| --- | --- | --- |
| 被除数→除数の10÷3 | 商3・余り1 | 一致 |
| 除数→被除数の10÷3 | 商0・余り0 | 不一致 |
| 除数→被除数の-10÷3 | 商0・余り0（期待-3・-1） | 不一致 |
| 除数3のまま被除数10→20 | 商3・余り1（期待6・2） | 不一致 |
| SDKの逆数計算と同じ順序で0xffffffff÷65537 | 商0（期待65535） | 不一致 |
| 商を1回読んだ後のDIRTY | 両経路で1（期待0） | 不一致 |
| 余りを2回読んだ後のDIRTY | Serialは0、WorkerBusは1（期待1） | Serial不一致 |

符号の異なるaliasへの切替、除数0の後の被除数更新でも古い結果が残りました。
一方、除数の更新、選択した符号付きoverflow、core間の独立計算は期待値に一致しました。
この修正前診断では、READY常時1・除数書き込み時の即時計算をソースで確認しました。
当時は8cycle境界とSDKの64bit除算コード全体を実行確認していません。
修正後の境界・SDK実行の確認結果は、冒頭の本体修正記録を参照してください。

仕様では**商の読み出しでDIRTYをクリアし、余りの読み出しでは維持**します。
修正前のSerialはどちらの結果でも2回読むとクリアし、WorkerBusは結果を読んでもクリアしません。
backendの既存の技術負債文書にあった「どの結果を読んでもクリア」は訂正しました。
DIRTY不整合は割り込み時の除算器状態の保存・復元判断に影響し得ますが、今回の
ClockCalc停滞の独立した原因とまでは確認していません。

[診断のソース・lockfile・生出力・ソースSHA](https://github.com/FuyukiYoneyama/picoem-picocalc/tree/main/docs/evidence/sio-divider-review-20261012)
をbackend側へ保存しました。この文書の初回登録時には新規テストを行っておらず、
今回の追検証としてレジスター診断を追加しています。ClockCalcは再実行していません。

再現時はbackendの `121d649` checkoutと、今回の診断資料を含むcheckoutまたは
配布bundleを別々に指定します。`121d649` 自体には診断の `main.rs` やlockfileは
含まれません。資料は同梱の `SHA256SUMS` で確認し、backend側の
[再現手順](https://github.com/FuyukiYoneyama/picoem-picocalc/blob/main/docs/evidence/sio-divider-review-20261012/README.md)
に従って独立したパスから読み込みます。

保存した旧診断は即時計算モデル用です。8cycleの計算時間を実装した後は、書き込み直後の
結果が未定義になり得るため、同じ診断の `matches_spec` を合否判定に使えません。
修正後用の診断ではemulated cycleを進め、時間上限内にREADY=1となったことを
確認してから余り・商を読みます。レジスターを直接呼ぶ現行診断では、READYを
ポーリングするだけでは時間は進みません。本体修正では時間に対応する回帰テストを
別途追加しました。旧診断の生出力とプログラムは履歴として保持しています。

保存済みClockCalc証拠の32ファイルとI2C fixtureはSHA-256が一致し、4つのreportの

キーが残り、0.8.78には時刻文字がありませんでした。過去の原本は保持しています。

## 当初の対策案と確認項目（履歴）

1. **両経路の計算開始を修正する。** SerialとWorkerBusそれぞれで、4つの
   operand aliasへの書き込みが計算開始・符号選択・DIRTY設定につながるようにします。
   Serialへの2箇所の追加だけではThreaded側の不具合が残ります。
2. **DIRTYの規則を修正する。** 商でクリア、余りでは維持するように両経路を直し、
   「2回でクリア」を要求する既存テストを仕様に沿う内容に置き換えます。
   結果レジスターへの直接書き込み、割り込みによる状態保存・復元も確認します。
3. **計算時間を別途モデル化する。** 8cycle完了、READYの遷移、計算中のoperand
   再書き込みによる再開始、結果への書き込みによる中断をcoreごとに確認します。
   計算開始の修正と時間精度の達成は、確認結果をそれぞれ記録します。
   時間モデルに対応する診断でcycleを進め、READY=1を確認してから結果を判定します。
4. **SDK除算を確認する。** 実際の64bit除算を、大きな入力・正負・繰返し・境界値で
   実行し、独立した整数計算の商と余りに一致すること、時間上限内に完了することを
   確認します。Serial／Threaded間で一致するだけでは、共通の誤りを除外できません。
5. **ClockCalcの因果関係を確認する。** 同一BIN、fixture、scenario、実行条件で
   修正前後を比較し、圧力補正の完了とfixtureから求めた圧力値、固定RTC時刻の期待する
   時計文字、その後の時刻更新、Escで電卓へ戻って操作できることを要求します。
   非黒画素数だけでなく文字・領域のパターンと入力後の動作を判定します。
   「keyイベント配送済み」だけではアプリが入力を処理した証拠になりません。
6. **再現物を揃えて保全する。** 新たな比較ではBIN・完全なdirtyソースまたはcleanな
   再現build・toolchain・backend commit・生ログ・画像・SHAを保存します。
   PC・LRの照合には、BINに対応するELFのSHAとsymbol照合・逆アセンブルの
   コマンド・出力も保存します。
   旧BINを回収できない場合は、新しいfirmwareでの比較と明記し、旧runとの同一比較を
   主張しません。受入条件を満たした後にaccepted backend pinの更新を判断します。

独自の除算呼び出しを被除数→除数の順にすれば局所的な回避は可能です。ただし、
ClockCalc側の式の変更、センサー無効化、待ち時間の追加ではSDK全体の動作を保証できません。
恒久対策はbackendの修正です。実機LCDの復旧は引き続き別の実機証拠で確認が必要です。
